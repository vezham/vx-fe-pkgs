# Tamizhi Intelligence + Browser — Implementation Task

You are working on the existing **Tamizhi implementation based on the DeepSeek Harness (DSH) fork**.

Do NOT rebuild Tamizhi from scratch.

First inspect the existing repository, architecture, packages, plugins, agent loop, tool system, session system, model abstraction, UI, and configuration. Extend the existing implementation cleanly and preserve existing functionality.

---2

## 1. Objective

Implement the foundation for:

1. **Tamizhi Intelligence**
2. **Tamizhi Browser**

The goal is to make Tamizhi capable of answering current/internet-based questions by using the user's browser as a web-access and web-execution layer.

Conceptually:

```text
User
  │
  ▼
Tamizhi
  │
  ├── Intelligence
  │     ├── Agent
  │     ├── Reasoning
  │     ├── Planning
  │     ├── Tool selection
  │     └── Answer synthesis
  │
  └── Browser Connector
        │
        ▼
   User's Browser
        │
        ├── Search
        ├── Navigate
        ├── Open pages
        ├── Read pages
        ├── Extract content
        ├── Follow links
        └── Return structured web context
```

The browser should perform web operations where practical, while Tamizhi performs the intelligence/reasoning.

The user should NOT need to manually browse search results for ordinary research questions.

---

# 2. Core Product Principle

Tamizhi should behave like:

> **AI + Search + Research Agent**

rather than merely:

> AI chatbot + search results.

Example:

User:

> "What are the latest changes in React and how do they affect my Vite application?"

Tamizhi should be able to:

```text
Understand question
       ↓
Determine that current web information is required
       ↓
Search web
       ↓
Identify useful sources
       ↓
Open relevant pages
       ↓
Extract useful content
       ↓
Compare / reason over sources
       ↓
Generate answer
       ↓
Provide source references
```

The browser activity should happen behind the primary Tamizhi UI whenever possible.

The user should primarily see Tamizhi's research state rather than raw browser navigation.

# 4. Tamizhi Intelligence

Define Tamizhi Intelligence as the layer responsible for deciding:

```text
Does this question require web access?
        ↓
Which tools should be used?
        ↓
Which searches should be performed?
        ↓
Which sources are useful?
        ↓
Which pages should be opened?
        ↓
What information is relevant?
        ↓
Is more research required?
        ↓
How should the final answer be synthesized?
```

The Intelligence layer should NOT itself contain browser-specific implementation details.

It should operate through abstract tools.

For example:

```ts
interface WebSearchTool {
  search(input: WebSearchInput): Promise<WebSearchResult[]>
}

interface WebOpenTool {
  open(input: WebOpenInput): Promise<WebPage>
}

interface WebReadTool {
  read(input: WebReadInput): Promise<WebPageContent>
}
```

The exact interfaces must follow the existing Tamizhi/DSH tool conventions instead of blindly copying these examples.

# 6. Browser Communication Architecture

The browser should be treated as an external execution environment.

Conceptually:

```text
Tamizhi Runtime
      │
      │ Browser Protocol
      ▼
Tamizhi Browser Extension
      │
      ▼
Browser
      │
      ▼
Internet
```

Do not tightly couple the Tamizhi Agent to Chrome-specific APIs.

Create a protocol/adapter boundary.

For example:

```text
Tamizhi Browser Protocol
        │
        ├── Chrome adapter
        ├── Edge adapter
        ├── Safari adapter (future)
        └── Desktop/browser adapter (future)
```

The agent should only know about capabilities.

It should not know:

```text
chrome.tabs
chrome.scripting
chrome.runtime
```

Those belong behind the browser adapter.

```text

etc.
```

Prefer background/service-worker/browser APIs where practical.

If a website requires a rendered page or a temporary tab, create a temporary browsing context and clean it up afterward where technically possible.

Do NOT assume every website can be accessed invisibly.

Some sites may require:

- user interaction
- login
- CAPTCHA
- permission
- visible browser state

Those cases must be handled explicitly.

# 10. Context and Token Efficiency

This is critical.

Do not send entire web pages to the model when unnecessary.

Implement progressive retrieval:

```text

 ↓

 ↓

 ↓
```


The browser connector should help reduce model context/token usage.

# 13. Browser Permissions and Security

Treat the browser as a security-sensitive boundary.

Do NOT give the extension unrestricted access by default.

Design explicit permission scopes.

Potential future scopes:

```text
web.search
web.read
web.navigate
web.interact
web.download
web.execute
```

Initially implement only the minimum permissions necessary for:

```text
search
open
read
```

Do not allow arbitrary browser actions merely because the agent requested them.

Sensitive operations should eventually require explicit user approval.

Examples:

```text
send message
submit form
purchase
delete
download sensitive data
change account settings
```

These should NOT be silently executed.

# 14. User-Owned Browser Context

One of the major goals is to allow Tamizhi to use the user's browser context where the user has authorized it.

For example:

```text
User is logged into:
GitHub
Notion
private documentation
company portal
etc.
```

Tamizhi Browser may eventually be able to read those pages through the user's existing browser session.

However:

- never bypass authentication
- never bypass access controls
- never exfiltrate unrelated page content
- never silently access unrelated tabs
- never transmit page data unless required by the current Tamizhi task
- respect explicit user permissions

The architecture must make these boundaries enforceable.

# 15. Cost Optimization

One of the major reasons for this architecture is cost reduction.

Target architecture:

```text
                 Vezham
                   │
             Tamizhi Runtime
                   │
              Intelligence
                   │
            Browser Connector
                   │
                   ▼
             User Browser
                   │
                Internet
```

This should reduce Vezham-side dependency on:

- browser rendering infrastructure
- large crawling fleets
- proxy infrastructure
- browser workers
- unnecessary bandwidth
- server-side page rendering

Do not claim that this makes web access free.

The user's browser/network performs some work, while model inference may still have a cost.

The architecture should make the cost boundary explicit.

# 27. Success Criteria

The implementation is successful when:

1. A user can ask Tamizhi a current web question.
2. Tamizhi recognizes that web information is required.
3. Tamizhi invokes the browser connector.
4. The user's browser performs the search/read operation.
5. Browser activity is normally hidden from the user.
6. Relevant content is extracted rather than sending unnecessary raw HTML.
7. Tamizhi reasons over the retrieved information.
8. Tamizhi produces a useful answer.
9. Sources are preserved and can be shown.
10. Web content cannot override Tamizhi's instruction hierarchy.
11. The browser connector is independent of the underlying model.
12. The architecture allows a future server-side web provider.
13. The architecture allows future local-model execution.
14. Existing DSH/Tamizhi functionality continues to work.
15. No unnecessary parallel framework or duplicate abstraction is introduced.
